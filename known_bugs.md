`bug_id: e4a1b7`
**Typing a capital `R` anywhere free-text could trigger a full app reload mid-keystroke, discarding what was being typed**: found live 2026-09-12 while testing the new "Add podcast" search box - searching "Radiolab" triggered a full library reload the instant the `R` landed, then every remaining character (`adiolab`) got dispatched as ordinary global keybinds against the freshly-reloaded app instead of the search box, which is what actually started an unrelated episode playing. Root cause: `main.rs`'s own `R`-triggers-refresh check runs on the same raw `KeyEvent` a second time, completely independently of whatever `App::handle_key` already did with it - so it never knew the key had just been typed into a text field. This isn't new to the podcast-add box: the exact same gap already existed for the pre-existing `/` search box and Settings > Update/Uninstall's password prompt, both of which also accept free text containing `R` - just apparently never noticed/reported before now. Fixed by adding `App::is_capturing_free_text()` (true while any of those three own the keyboard) and gating `main.rs`'s `R` check on it.

`bug_id: f1c8d9`
**A newly-created podcast always downloaded zero episodes, no matter what limit was requested**: the add flow's very first live test (via `GET /api/podcasts/:id/checknew`) downloaded 0 of a requested 3 episodes for a show with 866 available. Traced into the real Audiobookshelf server source: `Podcast.createFromRequest` stamps a freshly-created podcast's `lastEpisodeCheck` to the creation instant (`new Date()`), and `checknew` only ever considers episodes published *after* that timestamp - so a checknew call made immediately after creating a podcast will always find zero episodes, since everything in any real feed necessarily predates "right now". There's no endpoint to back-date that field. Fixed by seeding through `get_podcast_feed` + `POST /api/podcasts/:id/download-episodes` instead, which takes raw feed-episode objects directly with no date filtering at all (confirmed this is what the official web client's own per-episode download button uses) - verified live seeding exactly 3 and 5 episodes correctly, newest-first, via both the name-search and direct-RSS-URL add paths.

`bug_id: a2e6c4`
**Removing (or adding) a podcast could leave the library showing stale data indefinitely if no key was pressed afterward**: `library_needs_reload`'s consumption was nested entirely inside "a key was just pressed this tick" - fine for its original two uses (`R`, a Settings > Library switch), both of which are themselves triggered by a keypress in the same instant. The new podcast add/remove flows set this same flag from a background poll that resolves *between* keystrokes, once a spawned create/delete call actually finishes - so the reload sat pending, and the just-removed item kept showing, until the user happened to press anything at all. Fixed by moving the reload check to run unconditionally every loop tick in `main.rs`, and having `R` simply arm the same flag rather than reinit-ing inline - confirmed live that both podcast add and remove now refresh the library automatically with no extra keypress needed.

`bug_id: c7f2d4`
**Continue Listening can reorder while a session is starting, so a key pressed right after can land on the wrong row**: found live 2026-09-05 while re-testing `9bacac` below. Started playing "Murder on the Orient Express" (row 2 of 4), waited ~2s, then pressed `j` (expecting to move to row 3, "The Three Musketeers") followed immediately by `l` - the log showed it actually started "Buy Back Your Time" instead, an item that a `R` refresh moments earlier had placed at row 0, not row 3. No data corruption resulted (each item's own server-side position stayed correct and independent - see `9bacac`'s resolution below), but the wrong book got played.

Root-caused 2026-09-12 by reading `render` in `src/ui/tui.rs` (the "pin the actively-playing item to the top" block, just above `home_rows`): this is deliberate, documented behavior, not a stray defect - it reorders Continue Listening to pin whatever just started playing to row 0 on the very next render (~200ms later), and its selection-tracking is actually correct (it captures the selected id before reordering and re-finds that same id's new position afterward, so the highlighted row correctly follows the now-playing item). The reported symptom is a direct, fully-expected consequence of that: pressing play on row 2 pins it to row 0 almost immediately; a `j` press 2 seconds later moves the cursor from row 0 to row 1 - which is a *different* book than row 3 used to be, because the whole list shifted underneath. Nothing was stale, corrupted, or racing; the app did exactly what its code says to do.

Marked FIXED (not a defect) 2026-09-12: decided to keep the pin-to-top behavior as-is rather than soften or remove it - it's a deliberate, valued feature ("reacts as soon as playback starts"), and the only "fix" available would mean either delaying a feature that's supposed to be instant, or dropping it entirely in favor of waiting on the server's own next-refresh ordering. Closing as understood/working-as-intended; reopen if a real desync (not just "reordered while you were looking elsewhere") turns up.

`bug_id: 3f729c`
**Loading time was slow for libraries with a lot of items**: not optimized for a library with a lot of items (long start loading and refresh time). Measured and substantially improved 2026-07-29 by instrumenting `App::new` against a real 22-podcast library: startup was **17.5s**, of which ~14s was sequential N+1 HTTP - one request per item, each awaited before the next was issued. Three such loops were found and made concurrent: the per-podcast episode-list fetch in `App::new` (9.8s over 22 podcasts, ~450ms each - the single biggest cost), the per-episode progress lookup in `get_library_perso_view_pod.rs` (~230ms each), and the per-book progress lookup in `App::new`'s Continue Listening path (same shape, only hit by book libraries). All three now fan out via `futures::stream::...buffered(MAX_CONCURRENT_REQUESTS)` (8 at a time, see `src/utils/http_client.rs`). **`buffered`, never `buffer_unordered`** - results feed straight into index-aligned parallel arrays and would silently desync if they came back in completion order. Result: **17.5s → 8.4s**, verified live along with the array alignment itself (Home rows and Library→Episodes both checked at index 0 *and* a non-zero index, metadata matching the right podcast in each case). Benefits the periodic podcast refresh and `R` too, since both re-run these paths.

A second pass on 2026-07-29 then overlapped the three independent startup round-trips - the Home data (`fetch_podcast_home_data` / `get_continue_listening`), the full library listing (`get_all_books`), and the `check_update` GitHub call - with `tokio::join!`. They only ever needed `id_selected_lib`, so running them in sequence just summed their latencies (~1.8s + ~2.4s + ~0.5s); driven concurrently that phase measures a steady **1.8-2.1s**, about the slowest of the three rather than their total. (`tokio::join!` specifically, not building futures and awaiting them later - Rust futures are lazy, so an unpolled future isn't running and sequential awaits would have been exactly as slow as before.) **Startup is now ~7.0-7.6s, down from 17.5s** - measured over several runs, with array alignment re-verified after the restructure.

2026-07-29's analysis found ~5s of the remaining ~7s was the per-podcast episode-list fan-out - not worth more concurrency (raising `MAX_CONCURRENT_REQUESTS` to 16 measured no improvement over 8, confirming the server is throughput-bound), but fetched at startup purely so it's ready *if* the user opens a podcast from Library - a genuine architectural lazy-loading candidate, left for its own pass.

That pass happened 2026-07-30. `App::new()` no longer waits on the per-podcast episode-list fetch (`fetch_all_pod_ep`) at all - it's spawned as a background task returning through a `oneshot` channel, and a new `App::poll_pod_ep_fetch()` (called every render-loop iteration from `main.rs`, mirroring the existing `poll_update_uninstall_event` pattern) merges the result into `self` the moment it arrives. This is background *pre-fetch*, not true per-podcast on-demand loading - all 22 podcasts still get fetched, just no longer blocking the first render - which matters because episode data also feeds the cross-podcast episode search (`render_search_book` re-filters every frame, so it picks up results automatically once the background fetch lands, no separate invalidation needed) - true on-demand-per-open would have left podcasts never explicitly opened permanently unsearchable.

The two places that read `all_*_pod_ep[index]` directly (the Library→Episodes and Search→Episodes screen transitions, plus their `_search` array variants) needed a real readiness guard, not just an empty-Vec default: `selected_library`/`selected_search_book`'s index is bounded by lists that *don't* depend on this fetch, so it can legitimately be out of bounds against the still-empty `all_*_pod_ep` arrays before the background fetch lands - an unguarded `[index]` would panic. Both sites now check `index >= array.len()` first and show "Still loading episode lists, try again in a moment..." instead of transitioning if so.

**Startup measured 17.5s → ~4.3-4.7s** on the same 22-podcast library (book libraries, which never had this cost, measured the same ~4.3s before and after - confirmed unaffected). Verified live: the readiness guard actually fires and recovers cleanly (forced deterministically with a temporary 30s artificial delay in `fetch_all_pod_ep` - the message appeared, no panic, no broken transition, then removed before committing); Library→Episodes and Search→Episodes both still open the correct podcast's real episode list once data arrives (checked at a non-zero index too); an episode opened via the search path still plays correctly end-to-end and closes cleanly on `Q`; book-library switching and playback unaffected.

`get_all_books` at ~2.4s (a single call returning the whole library listing) was the one piece left unaddressed at that point - needed server-side paging or a lazier Library view to improve further.

Re-measured 2026-08-31 by instrumenting `App::new` fresh against the same 22-podcast library: `get_all_books` itself is no longer the bottleneck it was (~245ms now, not ~2.4s - either the server or this specific library changed since the last measurement, not something this pass changed). Instead found a much bigger, previously-unmeasured cost: `Picker::from_query_stdio()` (asks the terminal what image protocol it supports, for cover art) took **~2s on its own** - bigger than every network round-trip in `App::new` combined. Worse, since `App::new()` re-runs on every `R` refresh and every library switch (not just true startup), that ~2s was being paid again on *every* one of those, for a value that can't actually change mid-session. Fixed by querying it once per process (a `OnceLock`) and cloning the cheap result on every subsequent `App::new()` call. Verified live: a refresh's total `App::new()` time dropped from ~3.5s to ~1.4s, with the picker query itself going from ~2s to ~20 microseconds; cover art still renders correctly afterward.

Marked FIXED 2026-09-05: every concrete bottleneck found across four measurement passes (startup N+1 HTTP, startup round-trip overlap, background episode pre-fetch, the per-refresh `Picker` query) has been fixed and verified live, and no further slow-loading report has come in since. Reopen with a fresh measurement if a specific library/scenario is still found to be slow.

`bug_id: 9d41ab`

`bug_id: 7c3e91`
**Install crashed copying the binary, and the install script asked for sudo far more than it needed to**: forcing through the fix above, the same live Solus retry hit `cp: cannot create regular file '/usr/local/bin': No such file or directory` - a fresh Solus VM simply doesn't have `/usr/local/bin` pre-created, and the script assumed it already existed. `bug_id: d4f2a7`
**Book playback could silently start at the wrong track/position for a book Audiobookshelf sends without a track `index`**: `AudioTrack.index` (added for the token-in-URL fix above) was a required, non-nullable field with no `#[serde(default)]` - if the server ever omits or nulls `audioTracks[].index` for a book (the code's own neighboring comment already documented this happening for podcast episodes "pre-v2.21.0", but the book path, unlike the podcast path, didn't tolerate it), `serde_json` fails the *entire* track array to deserialize, silently falling back to an empty `Vec` via `.unwrap_or_default()` - a book resumed deep into a later file would have streamed track 0 from the very start, with the resume position computed against the wrong track's offset. Fixed by giving `index` a custom deserializer that treats a missing or null value as `0`, matching the tolerance the podcast path already had.

`bug_id: e1c8b3`
**Settings > Update could misreport "Incorrect password" after authentication actually succeeded**: the `saw_prompt` flag added by the sudo-double-prompt fix (see `known_bugs.md`'s own sudo-fix history below) was set the first time any prompt appeared and never reset - if the user then entered the correct password/fingerprint and the script failed *later* for an unrelated reason (network drop, disk full, a checksum mismatch), the failure was still reported as `AuthFailed`, hiding the real error. Fixed by tracking `progressed_since_prompt` (whether any script output happened after the most recently answered prompt, before the process exited) alongside `saw_prompt` - `hello_absotui.sh` always produces further output once it's genuinely running (e.g. `tar -xvzf`'s own verbose output), so "prompted, then nothing before exit" now means auth genuinely failed, while "prompted, then real progress, then exit" correctly reports the actual unrelated error instead.

`bug_id: f3a9d6`
**Library screen could silently attribute the wrong series name/sequence to books once "group by series" was toggled on**: `collect_series_name_library`/`collect_series_sequence_library` (new for the Series-grouping feature) pushed one entry per library item unconditionally, while five sibling collectors (`collect_titles_library`, `collect_auth_names_library`/`_pod`, `collect_published_year_library`, `collect_desc_library`) and the pre-existing `collect_duration_library` silently *skipped* any item whose `media`/`metadata` was `None` instead of pushing a placeholder - exactly the parallel-array desync class this codebase's own CLAUDE.md warns about. A library item with missing/orphaned media anywhere but the end of the list would make the skipping arrays one element shorter from that point on, while the series arrays stayed full length - `build_library_rows`' indices (bounded by the shorter arrays) would then read the *wrong* book's series data from every subsequent index once grouped. Fixed by making all six skipping collectors always push a placeholder (`"N/A"`/`0.0`, matching `collect_ids_library`'s existing pattern) instead of skipping, so every per-book array is now guaranteed the same length as `results` - the actual invariant that needed to hold, not just matching one sibling's behavior.
